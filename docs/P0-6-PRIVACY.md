# P0-6 개인정보 경계와 적용 조건

## 변경한 계약

P0-5는 `couples/{cid}/tastes`의 상대 태그와 원본 SHA-256을 클라이언트가 읽고 순위를 계산했습니다.
P0-6에서는 **작성자의 기기**가 본인 취향·본인 후보 분류·비공개 제외 목록으로 순위를 계산합니다.
상대에게 전달하는 새 문서는 `couples/{cid}/recommendations/{authorUid}`이며 필드는 `urls`, `updatedAt`뿐입니다.
태그, 원본 해시, 추천 이유, 점수, 원본 이벤트를 전달하지 않습니다.

| 데이터 | 읽기 | 쓰기 |
|---|---|---|
| users/uid, saved, preferences/taste | 본인 | 기존 본인 검증 유지 |
| 기존 couples/cid/tastes/uid | 본인만 (이전 데이터 복구) | 금지 |
| 기존 couples/cid/events/id | 이벤트 작성자만 | 금지 |
| recommendations/uid | 활성 커플 구성원 | 활성 구성원 중 해당 작성자만 |

새 추천 목록은 기존 공개 후보 10개 안에서 최대 5개, 중복 없이 정규화된 URL만 허용합니다.
추가 필드, 임의 호스트/URL, 오래된 시각, 다른 작성자 사칭을 거부합니다.
연결 해제 시 읽기가 거부되고 클라이언트의 수신 목록도 비워집니다.
계정 변경 시 listener generation과 개인 후보 캐시를 분리합니다.
트랜잭션은 시작한 사용자 ID의 문서 경로를 사용해 계정 변경 중 다른 사용자에게 쓰지 않도록 보완했습니다.

## 기존 데이터와 기능 보존

추천 엔진의 정렬·가중치·중복 제거·원본 제외는 유지했습니다. 계산 위치와 전달 형식을 바꿨습니다.
후보 수동 분류는 **내 취향으로 연인에게 보낼 추천**을 계산하는 데 사용합니다.
상대가 보낸 추천에는 내 기기에서 분류한 후보 표시만 덧붙이며 상대 비공개 태그로 재정렬하지 않습니다.
기존 개인 취향과 보관함은 삭제하지 않았습니다. 오래된 본인 커플 취향을 개인 영역으로 보존하는 이전 경로를 유지했습니다.
Fake 저장소에도 기존 JSON을 읽을 수 있도록 기본값을 둔 개인 후보 분류 필드만 추가했습니다.

## 보장 범위와 잔여 한계

- FakeBackend는 **같은 기기 내부의 테스트 저장소**입니다. 서버 권한을 증명하거나 두 폰을 동기화하지 않습니다.
- Firestore 규칙은 로컬 파일로만 변경했습니다. 운영 배포나 운영 권한 변경은 하지 않았습니다.
- 기존 서버 규칙이 남아 있으면 구버전 클라이언트가 옛 공유 태그/해시를 읽을 수 있습니다.
  새 클라이언트로 바꾸는 것만으로 기존 운영 데이터의 접근이 차단되지는 않습니다.
- 새 규칙에서는 새 출력 문서만 허용하므로 구버전 클라이언트의 옛 공유 쓰기가 거부됩니다.
  규칙·클라이언트 동시 적용과 이전 계획을 별도 검토해야 합니다.
- 전체 후보 10개 중 9개를 모두 보내면 누락된 원본을 역으로 특정할 위험이 있어 출력은 상위 최대 5개로 제한합니다. 후보를 가짜로 채우지 않습니다.
- 공개 후보 URL의 선택·순서·갱신 시각으로 취향을 추측할 수 있습니다. 완전한 추론 방지·암호학적 비공개를 보장하지 않습니다.
- 이미 상대가 읽은 과거 정보를 연결 해제 후 회수하거나 원격 삭제할 수 없습니다.
- 추천은 기존 후보 URL과 수동 분류 기반입니다. Instagram 전체 콘텐츠 검색·영상 분석·스크래핑이 아닙니다.

## 검증과 출시 전 조건

개인 입력 미노출, 원본 제외, 출력 정렬 변경, 재시작·재연결 보존은 JVM 회귀 검사를 실행합니다.
Firestore 실제 권한 판정은 공식 Emulator로 검증해야 합니다. 네트워크로 막힌 검사는 PASS로 대체하지 않습니다.
기존 규칙 테스트는 실제 11개였습니다(P0-4의 개인 취향 테스트 포함).
10개로 고정된 검증 래퍼를 수정하고 신규 출력·개인정보 검사 2개를 추가해 총 13개를 요구합니다.
운영 적용 전 13개 모두 성공, 실제 두 계정/두 기기 검증, 이전 계획 검토 및 별도 배포 승인이 필요합니다.
